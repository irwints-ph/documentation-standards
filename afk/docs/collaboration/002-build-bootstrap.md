# 🚀 Build Bootstrap

---

## Purpose

The Build Bootstrap prepares both Human Collaborators and AI Collaborators before beginning a Build session.

Its purpose is not to explain **what** is being built.

Its purpose is to establish **how collaboration should begin**.

A successful Build session starts from shared understanding rather than isolated prompting.

---

# Why Build Bootstrap Exists

Engineering projects accumulate decisions over time.

Without a common starting point, new collaborators often:

* make unnecessary assumptions,
* duplicate previous work,
* redefine existing architecture,
* or solve problems that have already been answered.

The Build Bootstrap reduces reconstruction by establishing a common engineering mindset before implementation begins.

---

# Build Philosophy

A Build session should never begin with code.

It begins with understanding.

Engineering should continue from existing knowledge rather than recreate it.

The first implementation is not writing software.

The first implementation is understanding what already exists.

---

# Build Mindset

Every collaborator should begin by asking:

* What are we trying to grant?
* What already exists?
* What has already been decided?
* What is the smallest useful implementation?
* What observation are we trying to create?

Implementation exists to create meaningful observations.

---

# Before Building

Do **not** begin implementation immediately.

Instead:

1. Establish the collaboration.
2. Synchronize operational context.
3. Understand the active wish.
4. Confirm current objectives.
5. Begin implementation.

---

---

# Responsibilities

## Human Collaborator

The Human Collaborator should:

* provide the current operational context,
* identify the active wish,
* authorize implementation,
* evaluate observations,
* and determine when a wish has been granted.

---

## AI Collaborator

The AI Collaborator should:

* read before generating,
* preserve existing engineering decisions,
* avoid inventing architecture,
* build from current understanding,
* ask questions when uncertainty appears,
* and request authorization before implementation when appropriate.

---

# Engineering Principles

A Build session should follow these principles.

## Understand First

Implementation follows understanding.

---

## Build Small

Build only enough to create the next meaningful observation.

---

## Preserve Decisions

Existing engineering knowledge should be extended rather than replaced.

---

## Observe Continuously

Every implementation should create observable results that improve future engineering decisions.

---

## Preserve Continuity

A Build session should conclude with enough preserved context that future collaborators can continue naturally.

---

# When to Pause

Pause implementation when:

* project purpose is unclear,
* the active wish cannot be identified,
* existing documentation appears inconsistent,
* architecture is uncertain,
* or implementation would require assumptions rather than understanding.

Collaboration should resolve uncertainty before implementation continues.

---

# Exit Condition

A Build session does not necessarily end because all possible functionality has been implemented.

It pauses when:

* the current objective has been advanced,
* observations have been recorded,
* evidence has been preserved,
* WWAN has been updated,
* and the next collaborator can continue without reconstructing prior work.

# Closing Thought

Build Bootstrap does not prepare collaborators to write code.

It prepares collaborators to understand the engineering journey they are joining.

Shared understanding reduces assumptions.

Reduced assumptions improve engineering.

Understanding first.

Build second.

Learn always.
